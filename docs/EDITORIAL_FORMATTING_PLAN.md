# 逐字稿排版與編輯標準化計劃（對標《釋量論·成量品 32-1.pdf》範本）

## 一、可行性評估

**結論：完全可行，且可與現有「影音時間軸同步」架構相容。**

- **資料結構相容性**：現有講次 JSON（`paragraphs[].sentences[]`）已將「義理段落（`p_k` + `heading`）」與「影音時間軸句子（`sent-X` + `start`/`end`）」分層。只要在底層保留 `sent-X` 的時間錨點，就能把段落合併與排版粒度調整到與範本相同的 150–350 字自然段，而**不影響點擊句子跳轉音訊／影片的功能**。
- **需注意的技術邊界**：
  1. **細粒度句界 vs. 完整長句標點**：範本中的分號（`；`）、破折號（`──`）與冒號引述常橫跨 ASR 的 2～3 個 `sent-X`。因此標點校對必須以「整段」為視窗協作，不能單句孤立判斷。
  2. **語氣保持與防誤刪**：範本刪除了無意義的「呢、啊、那」等口語雜訊，但完整保留了法師的設問節奏、實義副詞（如「剛好」「因此」）及「（學員：……）」互動。這需要透過已驗證的「Prompt 紅線 + 程式化安全閘門」來把關。

## 二、範本格式標準拆解（取自《釋量論·成量品 32-1.pdf》）

### 1. 標題與層級規範
- **講次標頭 Metadata**：呈現課程名稱、作者／翻譯／講解法師、講次與主題副標（如 `第一講（調整學法的動機）`）。
- **主題式編號小標（`N. 簡明義理標題`）**：
  - 格式：`1. 解釋開經偈`、`2. 一切問題都源自於不了解真相`、`3. 破除學佛的錯誤觀念`……
  - 粒度：每 **3～6 個自然段**（約講課 5～10 分鐘或義理大轉折處）設一個小標，避免碎片化。

### 2. 分段規範
- **自然段長度**：每段約 **150～350 字**（3～6 個完整句子），圍繞單一論點或譬喻展開。
- **短句／破碎段整併**：將 ASR 過度切碎的單句或純停頓片段併入所屬義理段落（底層仍保留各自 `sent-X` 與時間戳）。
- **互動與儀軌獨立成行**：如 `大眾請合掌。`、`南無本師釋迦牟尼佛（三稱）`、`（學員：……）` 可保持清楚辨識。

### 3. 標點與用字規範（臺灣繁體書面語）
| 標點 / 用字 | 使用規範 | 範本實例 |
|---|---|---|
| 引號 `「」` | 引用經論、專有名詞、內心獨白、自問自答 | `所謂的「見」，指的是見解`、`「我是一個想要了解真相的人嗎？」` |
| 書名／篇名號 `《》` `〈〉` | 經論／偈頌書名用 `《》`，品名／地名／章節用 `〈〉` | `《釋量論》`、`《開經偈》`、`《四百論》`、`〈聲聞地〉` |
| 全形雙破折號 `──` | 語氣轉折、同位語定義、引出具體理由或例子 | `它的對境──我最重要`、`苦諦的四種行相──無常、苦、空、無我` |
| 分號 `；` | 並列分句、正反對比、因果對照 | `愛自己，不見得快樂；但是愛他人，一定會快樂。` |
| 冒號 `：` | 引出問句、舉例、定義或引文 | `請問：以我為例…`、`例如：殺生、偷竊…` |
| 問號 `？`／驚嘆號 `！` | 設問與反問必用 `？`；強調語氣適度用 `！` | `這代表什麼？`、`早就展現出來了！` |
| 頓號 `、` | 並列詞語或四字科判名相 | `苦、集、滅、道`、`殺生、偷竊、詐欺、霸凌` |
| 稱代與慣用字 | 稱佛陀用「`祂`」；思惟用「`思惟`」、布施用「`布施`」、毗婆舍那用「`毗婆舍那`」（依講堂慣用） | `祂認識了無常`、`反覆地思惟`、`法布施` |

### 4. 口語冗詞處理尺度（預設強制標準：不改寫，但必清冗詞、補順句子）
- **核心原則**：**禁止整段改寫或替換法師原本的用詞與講法**，但**必須清除口語冗詞並依語意補順句子與標點**，不得把滿篇「呃、嗯、啊」的原始口語停頓留作最終成稿。
- **必須清除**：
  - 純停頓發語詞與填充音：`呃`、`嗯`、`啊`、`喔`、`欸`（非感嘆／引文語氣時）
  - 句首無義過渡：`好，`、`那，`、`好，那`、`這個`、`就是`（僅作口頭禪緩衝時）
  - 結巴重複詞：`這個這個`、`我們我們`、`波羅波羅蜜多`、斷裂半字
- **必須保留並補順**：
  - 實義副詞／邏輯連詞（`剛好`、`因此`、`其實`、`所以`、`如果`）、法師設問節奏（`對不對？`、`為什麼？`）及互動問答（`（學員：……）`）。
  - 清除冗詞後，將原本被 `呃、嗯、啊` 切碎的相鄰短句依語意補順、補齊書面語標點（`，`、`；`、`──`、`：`）。

## 三、分階段實施計劃

### Phase 1：建立「範本對齊的排版規範設定與安全閘門」（核心規則與品質護欄）
1. 在 `scripts/lib/fluentPolishAudit.js` 補入：
   - 依範本標準撰寫的系統提示詞（含 `──`、`；`、`：`、`《》`、`「」`、「祂」與問句規範）。
   - **程式化安全閘門**：
     - 禁止跨句搬移文字（比對相鄰句，攔截把下一句文字拉進上一句的提案）。
     - 禁止誤刪實義副詞與邏輯連詞（如 `剛好`、`已經`、`因為`、`所以`、`如果`、`沒有`、`不要`）。
2. 建立段落重組模組（`scripts/lib/paragraphLayoutPlanner.js`）：
   - 依據語意轉折與字數目標（150～350 字／段）重新合併過碎的 `paragraphs[]`，並產出 `1. ...`、`2. ...` 編號義理小標，同時完整保留每個 `sent-X` 的 `id`、`start`、`end` 與順序。

### Phase 2：單講試點驗證
1. 對試點講次執行完整管線：
   - 步驟 A：名相漏字偵測 + GX10 雙軌局部重辨識
   - 步驟 B：`polish_session_fluent.mjs`（套用範本標點與口語精簡＋安全閘門驗證）
   - 步驟 C：段落合併與 `N. 主題小標` 排版重組
2. 產出前後對照閱讀預覽（Markdown / HTML），人工抽檢確認：
   - 標題粒度、段落長度、標點（`──`、`；`、`：`、`《》`）是否貼近《釋量論·成量品 32-1.pdf》水準。
   - 點擊網頁每句仍能精準跳轉 YouTube / 音訊時間軸。

### Phase 3：網頁端排版渲染優化 & 匯出支援
1. 檢視 `src/App.vue` 閱讀器 CSS：確認多句合段渲染時，`N. 小標`、段落間距與字體行高（1.8–2.0）呈現接近 PDF 講記的閱讀質感。
2. 讓匯出功能（Markdown / 純文字 / 列印版）同步支援輸出與範本一致的講次標頭、編號小標與分段排版。
3. 確認 Pilot 滿意後，將修訂與流程腳本合併上線，再逐步批次推廣至其他講次。

## 四、通用執行資訊、模型備援與品管規範（供未來所有 Agent 遵循）

### 1. LLM 服務與備援優先順序（eNeural 優先於 GX10 Qwen）
- 針對校對潤飾及導讀摘要備援：
  1. **eNeural（優先）**：`https://agents.eneural.ai/v1`（模型 `glm53-flash`），金鑰由環境變數 `ENEURAL_API_KEY`（或專案根目錄受 `.gitignore` 保護的 `.env`）讀取，呼叫時須傳入 `chat_template_kwargs: { enable_thinking: false }`。速度較快，MiniMax 額度不足或離線時優先使用 eNeural。
  2. **GX10 本地 vLLM（次要備援）**：`http://100.113.144.100:18765/v1`（模型 `nvidia/Qwen3.8-27B-NVFP4`，透過 Tailscale 免金鑰存取）。僅在 eNeural 無法連線或無金鑰時作為備援。
  3. 導讀摘要 `content_overview_pipeline.mjs` 預設仍先嘗試 MiniMax；若遇 HTTP 500/429/2056 額度限制，自動依「**eNeural → GX10 Qwen**」順序備援。
- **單線程／低併發限制**：呼叫 Local model（GX10）或 eNeural model 時，**同一時間只跑 1 個 process / 1 個請求（`concurrency = 1`）**，避免多路並發造成推論排隊或逾時。

  1. **佛法名相、經論名稱、人名與偈頌**：
     - 經典與論典：《瑜伽師地論》（防誤為《語邪實地論》/《與其事理論》/《語學士定論》/《事例論》）、《入菩薩行論》（寂天菩薩，防誤為「今天菩薩」）、《菩提燈論》、《釋量論》等。

### 4. 資料結構紅線與 `contentOverview` 同步規範
- **嚴禁空字串句子**：刪除冗句、重複句或純標點孤立句時，**不可將 `sentence.text` 設為 `""`**（會觸發 `asrIntegrityGate.test.js` 的 `Sentence text must be a non-empty string` 失敗），必須將該句物件從 `sentences[]` 移除，並濾除變成空的 `paragraphs[]`。
- **完整同步 `contentOverview` 與重算 `sourceDigest`**：任何講次內文有增刪或修改句子文字時，必須同步更新 `contentOverview` 中**所有包含 `evidence[]` 的四個陣列**（`mainPoints`、`discussionTopics`、`sections`、`referenceViews`——過濾已刪除的 `sent-id`、更新 `quote` 與現行句子完全一致），並呼叫 `scripts/content_overview_pipeline.mjs` 匯出的 `computeSourceDigest(transcript)` 重新計算寫入 `contentOverview.sourceDigest`，否則 `npm run summaries:audit` 會失敗。

### 5. 驗證與 Git / GitHub 交付規範
- **必跑三道驗證**：提交 PR 前須通過：
  1. `npm run summaries:audit`（確認 `complete: true` 且 `invalid: 0`）
  2. `npm run test:v2`
  3. `npm test`
- **明確暫存檔案（Explicit `git add`）**：僅 `git add` 本次任務修改的明確檔案路徑，避免將工作區無關檔案（如測試報告或本地暫存）誤納入 commit。
- **PR 合併方式**：本儲存庫禁止 Squash merge；PR 通過 GitHub Actions（`Completion Acceptance`）後統一使用 Merge commit（`gh pr merge <num> --merge --delete-branch`）。
