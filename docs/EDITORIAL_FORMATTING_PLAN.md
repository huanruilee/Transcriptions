# 逐字稿排版與編輯標準化計劃（對標《釋量論·成量品 32-1.pdf》範本）

## 一、可行性評估

**結論：完全可行，且可與現有「影音時間軸同步」架構相容。**

- **資料結構相容性**：現有講次 JSON（`paragraphs[].sentences[]`）已將「義理段落（`p_k` + `heading`）」與「影音時間軸句子（`sent-X` + `start`/`end`）」分層。只要在底層保留 `sent-X` 的時間錨點，就能把段落合併與排版粒度調整到與範本相同的 150–350 字自然段，而**不影響點擊句子跳轉音訊／影片的功能**。
- **需注意的技術邊界**：
  1. **細粒度句界 vs. 完整長句標點**：範本中的分號（`；`）、破折號（`──`）與冒號引述常橫跨 ASR 的 2～3 個 `sent-X`。因此標點校對必須以「整段」為視窗協作，不能單句孤立判斷。
  2. **語氣保持與防誤刪**：範本刪除了無意義的「呢、啊、那」等口語雜訊，但完整保留了法師的設問節奏、實義副詞（如「剛好」「因此」）及「（學員：……）」互動。這需要透過已驗證的「Prompt 紅線 + 程式化安全閘門」來把關。

## 二、範本格式標準拆解（取自《釋量論·成量品 32-1.pdf》）

### 1. 標題與層級規範
- **講次標頭 Metadata**：呈現課程名稱、作者／翻譯／講解法師、講次與主題副標（如 `第一講（調整學法的動機）`）。
- **主題式編號小標（`N. 簡明義理標題`）**：
  - 格式：`1. 解釋開經偈`、`2. 一切問題都源自於不了解真相`、`3. 破除學佛的錯誤觀念`……
  - 粒度：每 **3～6 個自然段**（約講課 5～10 分鐘或義理大轉折處）設一個小標，避免碎片化。

### 2. 分段規範
- **自然段長度**：每段約 **150～350 字**（3～6 個完整句子），圍繞單一論點或譬喻展開。
- **短句／破碎段整併**：將 ASR 過度切碎的單句或純停頓片段併入所屬義理段落（底層仍保留各自 `sent-X` 與時間戳）。
- **互動與儀軌獨立成行**：如 `大眾請合掌。`、`南無本師釋迦牟尼佛（三稱）`、`（學員：……）` 可保持清楚辨識。

### 3. 標點與用字規範（臺灣繁體書面語）
| 標點 / 用字 | 使用規範 | 範本實例 |
|---|---|---|
| 引號 `「」` | 引用經論、專有名詞、內心獨白、自問自答 | `所謂的「見」，指的是見解`、`「我是一個想要了解真相的人嗎？」` |
| 書名／篇名號 `《》` `〈〉` | 經論／偈頌書名用 `《》`，品名／地名／章節用 `〈〉` | `《釋量論》`、`《開經偈》`、`《四百論》`、`〈聲聞地〉` |
| 全形雙破折號 `──` | 語氣轉折、同位語定義、引出具體理由或例子 | `它的對境──我最重要`、`苦諦的四種行相──無常、苦、空、無我` |
| 分號 `；` | 並列分句、正反對比、因果對照 | `愛自己，不見得快樂；但是愛他人，一定會快樂。` |
| 冒號 `：` | 引出問句、舉例、定義或引文 | `請問：以我為例…`、`例如：殺生、偷竊…` |
| 問號 `？`／驚嘆號 `！` | 設問與反問必用 `？`；強調語氣適度用 `！` | `這代表什麼？`、`早就展現出來了！` |
| 頓號 `、` | 並列詞語或四字科判名相 | `苦、集、滅、道`、`殺生、偷竊、詐欺、霸凌` |
| 稱代與慣用字 | 稱佛陀用「`祂`」；思惟用「`思惟`」、布施用「`布施`」、毗婆舍那用「`毗婆舍那`」（依講堂慣用） | `祂認識了無常`、`反覆地思惟`、`法布施` |

### 4. 口語冗詞清除、碎句合併與依語意補順規範（核心原則）
- **核心原則（不整篇改寫，但必除冗詞、必合碎句、必依語意補順）**：
  - 早期規範曾寫「忠實逐字、不得刪合句子」，初衷是為了防止 AI 將法師講課「整大篇改寫或濃縮成大綱摘要」，**絕非保留發語詞、結巴與破碎斷句**。
  - **禁止事項**：禁止整段改寫、禁止改變法師原有的論證脈絡與口氣、禁止憑空捏造未講的內容、禁止刪除實義副詞與否定詞。
  - **強制執行事項（所有正式逐字稿一律適用）**：
    1. **徹底清除發語詞與口語贅詞**：凡是 `呃`、`嗯`、`啊`、`喔`、`欸`、無實義的句首/句中過渡詞（`好，那`、`那，`、`好，`、`就是說，`、`這個，這個`、`就是，嗯，`）、結巴重複詞（`這個這個`、`然後，然後呢`），**一律刪除**。若某個 `sent-X` 整句僅含發語詞或冗詞（如獨立一句 `呃，`、`嗯，`、`好，`、`那，`），必須將該句物件從 `sentences[]` 中移除。
    2. **合併被 ASR 切碎的單詞與子句（Clause Consolidation）**：當同一個詞或同一個連貫子句被 Whisper 切成多個 1～4 字的短句（如 `[sent-151] 也希望能夠，` + `[sent-152] 傳，` + `[sent-153] 達出去，`），**必須合併為單一完整 `sent-X`**（`也希望能夠傳達出去，`），並將時間軸更新為 `start = 首句.start`、`end = 末句.end`，消除詞語中間的碎逗號，確保每個 `sent-X` 都是語意完整的自然分句。
    3. **依語意補齊並順暢句子**：口語講述常有半截斷句、語序倒裝或因停頓造成的破碎短句；校對時**必須依前後文語意將破碎短句順成自然流暢、語意完整的句子**，並補齊殘缺的佛法名相與連接詞。
- **保留**：實義副詞／連詞（`剛好`、`已經`、`因此`、`其實`、`因為`、`所以`、`如果`、`沒有`）、法師設問節奏與互動問答（`（學員：……）`、`對不對？` 的適當反問）。

## 三、完整轉稿與品管單向流水線（Stage 0 ～ Stage 7）

所有課程轉稿與校對一律遵循以下單向順序，避免前後階段互相覆蓋或使摘要失效：

1. **Stage 0：前置領域知識建立（Domain Grounding）**
   - 確認講者、道場住持（如見岸法師）、教材底本、關聯經論（《瑜伽師地論》、《入菩薩行論》、《釋量論》等），建立課程專屬名相與同音易錯詞表。
2. **Stage 1：原始音訊轉寫與不可變備份（Raw ASR）**
   - 以 Whisper large-v3 轉出帶 `[start, end]` 時間戳的原始 `sent-X`，原始記錄留存備查。
3. **Stage 2：佛法名相／異常偵測 ＋ GX10 Whisper 局部重辨識與幻覺修復（先正字音，再順文句）**
   - 以 `dharmaTermAudit.js`（規則掃描）＋ `llmOmissionAudit.js`（語意異常偵測）找出疑似誤辨、漏字與幻覺迴圈。
   - 透過 SSH 呼叫 GX10（`100.113.144.100:8010`）切出目標音訊窗，單線程執行無提示詞（Raw）與帶佛學提示詞（Guided）雙軌重辨識，在進入順句前先還原正確字詞。
4. **Stage 3：清除口語冗詞、合併破碎短句與依語意補順（Fluent Consolidation & Polish）**
   - **步驟 3A（確定性冗詞句移除與碎句整併）**：執行 `consolidateFillersAndFragments`，刪除獨立成句的 `呃`、`嗯`、`啊`、`好，那` 等純冗詞句，並將被切碎的 1～3 字殘片與相鄰子句合併為完整分句（繼承首尾 `[start, end]`）。
   - **步驟 3B（LLM 語意補順與出版級標點）**：執行 `generateFluentPolishProposals` 與 `ensureParagraphPunctuation`，清除殘留口頭禪、依語意順暢句子並套用《釋量論·成量品 32-1.pdf》標點規範（`──`、`；`、`：`、`《》`、`「」`、「祂」），同時由安全閘門保護實義詞與否定詞不被誤刪。
5. **Stage 4：自然段重組（150～350 字）與主題編號小標**
   - 在冗詞清除、碎句合併定型後，由 `paragraphLayoutPlanner.js` 依語意轉折重組為每段 150～350 字的自然段（同步更新 `paragraph.start / end`），並每 3～6 段配置 `1. ...`、`2. ...` 編號義理小標。
6. **Stage 5：Agent 佛法專家逐段通讀審核（雙重驗收：義理精確 ＋ 文句流暢零冗詞）**
   - 主控 Agent 親自逐段通讀全文，同時確認「佛法名相與義理 100% 正確」及「零發語詞殘留（無 `呃/嗯/啊`）、無破碎逗號斷句、文句自然流暢」。遇有疑義音段立即以 GX10 Whisper 重聽確認。
7. **Stage 6：導讀摘要（`contentOverview`）生成／同步與 `sourceDigest` 鎖定**
   - **必須在內文與 `sent-X` 完全定稿後執行**：同步更新 `contentOverview` 四個 `evidence[]` 陣列（`mainPoints`、`discussionTopics`、`sections`、`referenceViews`），確保所有 `sentenceIds` 存在且 `quote` 與定稿句子完全一致，最後以 `computeSourceDigest(transcript)` 寫入 `sourceDigest`。
8. **Stage 7：自動化品管閘門（CI Tests）與 PR 合併發布**
   - 執行 `npm run summaries:audit`、`npm run test:v2`、`npm test`（含 `asrIntegrityGate.test.js` 的零發語詞／零碎句／零禁用錯字閘門），通過後以獨立分支提交 PR 並以 Merge commit（`--merge`）合併。

### 3. Stage 5：Agent 佛法專家逐段通讀審核（強制規範）
- **嚴禁僅以程式規則掃描**（`U+FFFD`、半形標點、時間軸等）代替專家審核。
- 每講在自動化管線與程式規則檢查通過後，**主控 Agent 必須親自逐段通讀該講全文**，以佛法專家角度核對：
  1. **佛法名相、經論名稱、人名與偈頌**：
     - 經典與論典：《瑜伽師地論》（防誤為《語邪實地論》/《與其事理論》/《語學士定論》/《事例論》）、《入菩薩行論》（寂天菩薩，防誤為「今天菩薩」）、《菩提燈論》、《釋量論》等。
     - 常見名相與同音誤辨：暇滿人身（防「暇滿人生」）、意樂（防「利益」）、布施（統一不作「佈施」，防「不失」）、羼提（防「禪提」）、靜慮（防「禁律」「淨慮」「律」）、擐甲（防「幻甲」「換」）、惡作（防「悟作」）、對治（防「對峙」「對處」）、修持（防「羞恥」）、和合（防「合合」「合和」）、資糧（防「資料」「質量」）、迴向（防「回向」）、偈頌（防「寄送」）、貪欲（防「貪慾」）、貪著（防「攤著」）、瞋心／瞋恚／理瞋（防「嗔」「稱心」「秤心」「理稱」）、掉舉（防「調舉」）、輕安（防「清安」）、欲界定（防「預界定」）、欣上厭下（防「心上焰下」）、初證／初得（防「出正」「出得」）、諦實／諦察（防「地實」「地茶」）、勝義諦／勝義抉擇（防「聖一地」「聖意抉擇」）、聞思修／聞所成慧／思所成慧（防「文所成慧」「思索成慧」）、緣空性／緣著（防「圓空性」「圓著」）、無二根本定（防「無惡根本定」）、因明／宗因喻／隨遍／倒遍／異品遍／論式（防「英明」「中英域」「道遍」「導片」「論事」）、九住心／放捨力／本生／初地／人名（如周利槃陀伽、陳那論師、妙境老和尚）等。
  2. **語意連貫、口語誤辨與零發語詞／零碎句檢查**：
     - 頁碼與同音字：如頁碼誤辨（`108年` → `108頁`、`葉馬` → `頁碼`）、同音字（`法器` → `佛七`、`做` → `坐`、`心醒` → `欣喜`、`死屍` → `廚師`、`胡家胡味` → `狐假虎威`）、漏字／漏否定詞等。
     - **零發語詞與流暢度驗收（強制項）**：確認全文已徹底清除 `呃`、`嗯`、`啊`、`喔`、`好，那` 等無實義發語詞與口頭禪，且無被逗號切碎的單詞／短句（如 `傳，達出去，`），所有句子皆依語意補齊為通順自然的句子。
  3. **ASR 雜訊、幻覺與重複句清除**：檢查是否有 2 句以上重複句、長段幻覺迴圈、外文／亂碼幻覺、未清除的佔位字串（如 `【⚠️`、`無法辨識原意`、`待確認`）與孤立標點（如單獨 `！`）；遇到無法從上下文還原的壞段，須調用 GX10 Whisper 重聽原音檔片段確認。
- 凡在人工通讀中發現之系統性誤辨規則，須同步沉澱更新至 `dharmaTermAudit.js`、`fluentPolishAudit.js` 或課程管線腳本。

### 4. 資料結構紅線與 `contentOverview` 同步規範
- **嚴禁空字串句子**：刪除冗句、重複句或純標點孤立句時，**不可將 `sentence.text` 設為 `""`**（會觸發 `asrIntegrityGate.test.js` 的 `Sentence text must be a non-empty string` 失敗），必須將該句物件從 `sentences[]` 移除，並濾除變成空的 `paragraphs[]`。
- **完整同步 `contentOverview` 與重算 `sourceDigest`**：任何講次內文有增刪或修改句子文字時，必須同步更新 `contentOverview` 中**所有包含 `evidence[]` 的四個陣列**（`mainPoints`、`discussionTopics`、`sections`、`referenceViews`——過濾已刪除的 `sent-id`、更新 `quote` 與現行句子完全一致），並呼叫 `scripts/content_overview_pipeline.mjs` 匯出的 `computeSourceDigest(transcript)` 重新計算寫入 `contentOverview.sourceDigest`，否則 `npm run summaries:audit` 會失敗。

### 5. 驗證與 Git / GitHub 交付規範
- **必跑三道驗證**：提交 PR 前須通過：
  1. `npm run summaries:audit`（確認 `complete: true` 且 `invalid: 0`）
  2. `npm run test:v2`
  3. `npm test`
- **明確暫存檔案（Explicit `git add`）**：僅 `git add` 本次任務修改的明確檔案路徑，避免將工作區無關檔案（如測試報告或本地暫存）誤納入 commit。
- **PR 合併方式**：本儲存庫禁止 Squash merge；PR 通過 GitHub Actions（`Completion Acceptance`）後統一使用 Merge commit（`gh pr merge <num> --merge --delete-branch`）。
