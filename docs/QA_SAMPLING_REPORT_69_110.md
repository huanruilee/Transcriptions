## 4. 發現的問題

### 🔴 嚴重問題：時間戳為合成/虛構數據，與實際音檔完全脫節

**這是本次 QA 最重要的發現。** 所有 5 個抽樣 session 的時間戳都是**合成產生的**，並非真實 ASR 對齊結果：

1. **段落時間戳**：每個段落一律恰好 **120 秒**（2 分鐘）長，無一例外。
2. **句子時間戳**：每個句子起始時間一律恰好 **8 秒**間距（120, 128, 136, 144, 152…），最後一句延伸至段落尾。
3. **總時長嚴重超標**：JSON 最後一段的 end 值（11400–15600s）是實際音檔時長（2126–3256s）的 **4.2–5.4 倍**。

| session | JSON 末段 end (s) | 實際音檔時長 (s) | 倍數 |
|---|---|---|---|
| 69A | 14160 | 3256.89 | 4.3× |
| 74B | 11880 | 2821.77 | 4.2× |
| 78B | 11400 | 2126.64 | 5.4× |
| 103A | 12480 | 2907.63 | 4.3× |
| 110B | 15600 | 3246.71 | 4.8× |

**影響**：前端 `app.js` 使用 `audio.currentTime = sentence.start`（點擊句子跳轉）與 `findSentenceIndexByTime`（播放時高亮當前句子）。由於時間戳是虛構的，這兩個功能都會失效——點擊句子會 seek 到音檔結束之後的位置，播放時也無法正確高亮對應句子。

**重要背景**：此問題**並非 69–110 批次特有**。經查證，早期 session（01、02A、30A、68A）同樣是 120s 段落 + 8s 句子間距，JSON 末段 end 同樣是實際音檔的 4–6 倍。這是**整個資料集的系統性問題**，非本次新轉譯引入的 regression。

### 🟡 次要問題：每 session 僅 1 個頁碼標記

每個 session 僅在開頭有 1 個 `[p.XX]` 標記（與 course.json pageRange 一致）。若一堂課跨越多頁，目前只標記起始頁。此為既有模式（先前 QA 報告亦已指出），非本次新增問題。

### 🟡 次要問題：內容繼承來源的少量 ASR 殘留

內容與 Obsidian 校正稿 100% 一致，但校正稿本身仍含少量 ASR 殘留，例如：
- 69A：「sellers 不會有那個作業的」（應為「也沒有」之類）
- 110B：「五五五」「一國」（應為「一類」）

這些是**繼承自校正來源**，非 JSON 轉換引入，且不影響整體可讀性。

## 5. 建議

1. **（高優先）重新對齊時間戳**：時間戳是平台「點擊跳轉 + 播放高亮」功能的核心。建議以真實音檔時長為基準，重新產生段落/句子時間戳（例如以 ASR word-level 時間戳對齊，或至少將段落時長壓縮至實際音檔時長內）。目前虛構時間戳使核心互動功能失效。
2. **（中優先）補齊頁碼標記**：若逐字稿跨越多頁，建議在對應位置補上 `[p.XX]` 標記，而非僅標記起始頁。
3. **（低優先）清理 ASR 殘留**：可針對「sellers」「五五五」等明顯殘留做一次性的術語校正（但需注意與校正稿來源同步）。
